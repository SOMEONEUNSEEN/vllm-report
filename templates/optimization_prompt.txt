## 分析流程（每个 commit 必须遵循）

### 步骤 1：提取基础字段
1. `sha`：full_sha 前 8 位
2. `full_sha`：commit 的 40 位 SHA
3. `date`：commit 日期，格式 YYYY-MM-DD
4. `title`：commit message 首行（去除前缀空格）
5. `pr_number`：从 message 正则提取 `#(\d+)`，提取不到填 null
6. `pr_url`：有 PR 号时填 `https://github.com/{repo}/pull/{pr_number}`，否则 null
7. `commit_url`：`https://github.com/{repo}/commit/{full_sha}`
8. `upstream_status`：默认 merged（commit 已在主分支）
9. `merged_at`：commit 的 ISO8601 时间（如可从 commit date 推断）
10. `author`：从 commit 数据的 author 字段提取 {name, email}
11. `labels`：从 commit message 或 PR 标签推断（如 [Bugfix]、[Performance]），无则空数组

### 步骤 2：提取 affected_files
- 从 commits 数据的 `files[].filename` 提取所有变更文件路径
- 若 commit 无 files 字段，从 message 的 diff stat 提取
- 若完全无法提取，affected_files 填 `["<unknown>"]`，low_confidence=true

### 步骤 3：判定 category
按 affected_files 路径匹配（取第一个命中项）：
- `vllm/v1/worker/gpu_model_runner.py`, `vllm/engine/` → core-engine
- `vllm/v1/attention/`, `vllm/v1/core/kv_cache*` → attention-kv-cache
- `vllm/model_executor/models/`, `vllm/models/` → model-architecture
- `vllm/model_executor/layers/fused_moe/` → moe-fusion
- `csrc/`, `vllm/_custom_ops.py` → operator-kernel
- `vllm/distributed/` → distributed
- `vllm/v1/worker/gpu/spec_decode/` → spec-decode
- `vllm/v1/kv_offload/` → kv-offload
- `vllm/model_executor/layers/quantization/` → quantization
- `vllm/lora/` → lora
- `vllm/multimodal/` → multimodal
- `vllm/config/` → config
- `vllm/v1/core/sched/` → scheduler
- `tests/`, `.buildkite/` → test-ci
- 其他 → other

跨模块 commit：取影响最大的模块（优先 core-engine > attention-kv-cache > distributed > 其他）

### 步骤 4：判定 ascend_value（必须引用架构上下文）
1. 检查 affected_files 是否命中 patch_impact_map 的任一 key
   - 命中 → patch_conflict=true, patch_matched_keys 填入命中的 key, ascend_value ≥ medium
2. 检查是否属于 definitely_affected_paths
   - 命中 → ascend_value=high 或 medium（视变更范围）
3. 检查是否属于 potentially_affected_paths
   - 命中 → 结合变更内容判断，ascend_value=medium 或 low
4. 检查是否属于 never_affected_paths 或纯平台特化代码（csrc/, flashinfer, rocm, cuda）
   - 命中 → ascend_value=none, migration_method=skip
5. 公共路径（gpu_model_runner.py 等）但未命中 patch_impact_map
   - ascend_value 视变更内容, patch_conflict=false

### 步骤 5：判定 change_type
- bugfix：message 含 fix, bug, crash, error, wrong, broken, regression
- performance：message 含 perf, optimize, speedup, faster, reduce overhead
- feature：message 含 add, support, implement, introduce
- refactor：message 含 refactor, cleanup, rename, reorganize

### 步骤 6：判定 priority（严格遵循矩阵）
| 条件 | 优先级 |
|------|--------|
| ascend_value=high 且 patch_conflict=true | P0 |
| ascend_value=high 且 change_type=bugfix | P0 |
| ascend_value=high 且 change_type=performance | P1 |
| ascend_value=medium 且 patch_conflict=true | P1 |
| ascend_value=medium 且 patch_conflict=false | P2 |
| ascend_value=low | P3 |
| ascend_value=none | skip |

### 步骤 7：选择 migration_method
- `cherry-pick`：公共路径，Ascend 无 patch 覆盖（patch_conflict=false）
- `patch-sync`：Ascend 通过 patch 覆盖的路径（patch_conflict=true）
- `idea-copy`：平台特化但思路通用，需用 Ascend 算子重写
- `config-align`：配置默认值/新增参数/API 调整
- `auto-inherit`：父类方法，未被 patch 覆盖（如 NPUModelRunner 继承 GPUModelRunner）
- `skip`：CUDA/ROCm 专用，Ascend 无对应场景（ascend_value=none）

### 步骤 8：生成 migration_steps（method ≠ skip 时必填，≥1 项）
每步必须可执行，包含具体文件/模块/验证方法。示例：
- ✅ "确认 NPUModelRunner 未覆盖 gpu_model_runner.py 的 _load_model 方法"
- ✅ "在 vllm_ascend/tests/ 添加 level-2 sleep/wake + LoRA 回归测试"
- ❌ "检查相关代码"（过于模糊）

### 步骤 9：生成 test_verification（priority ≤ P2 时必填，≥1 项）
列出需验证的测试场景。示例：
- "Ascend level-2 sleep/wake + LoRA 状态恢复验证"
- "NPUModelRunner 多卡分布式 sleep/wake 回归"

### 步骤 10：填写 ascend_impact_ref（如 analysis 数据存在）
引用 analyze_commits 的 ascend_impact 判定：
```json
{
  "ascend_affected": true/false,
  "functionality": "<来自 analysis 的 functionality 字段>",
  "source": "<analysis 文件日期，如 2026-08-06>"
}
```

## 文本约束

### R1：语言规范
- `optimization_point`、`ascend_value_reason`、`priority_reason`、`migration_steps`、`test_verification`：中文
- `title`、`category`、`change_type`、`migration_method`、`priority`、`status` 等枚举：英文
- `review_notes`、`confidence_reason`：中文

### R2：文本长度
- `optimization_point` ≤100 字，格式：动词+对象+效果（如"修复 sleep/wake 与 LoRA 的状态一致性"）
- `ascend_value_reason` ≤80 字，必须引用架构上下文（如"gpu_model_runner.py 是 NPUModelRunner 父类"）
- `priority_reason` ≤60 字

### R3：禁止模糊词
严禁使用"可能""也许""不确定""大概""也许会"。不确定时设 low_confidence=true 并填写 confidence_reason。

### R4：skip 规则
- migration_method=skip 时，ascend_value_reason 必须给出跳过理由
- 跳过理由类型：CUDA 专用 / ROCm 专用 / 无对应场景 / 平台特化代码

### R5：patch_conflict_detail
- patch_conflict=true 时必填，列出命中的 patch 路径
- 示例："命中 vllm.v1.worker.gpu_model_runner → vllm_ascend.patch.worker.block_table_patch"

## 边界情况处理

### B1：Merge commit
- 含 "Merge" 前缀的 commit：跳过分析，migration_method=skip, ascend_value=none
- ascend_value_reason 填 "Merge commit，无实质代码变更"

### B2：无 affected_files
- affected_files 填 `["<unknown>"]`
- low_confidence=true
- confidence_reason 填 "commit 无文件变更信息"

### B3：跨模块 commit（affected_files 跨多个 category）
- category 取影响最大的模块
- ascend_value 取最高值
- patch_conflict 只要任一文件命中即为 true

### B4：文档/CI commit（误入）
- 若 affected_files 全为 *.md, docs/, .buildkite/, *.yml
- migration_method=skip, ascend_value=none
- ascend_value_reason 填 "纯文档/CI 变更，无代码影响"

### B5：vllm-ascend 仓库的 commit
- repo=vllm-project/vllm-ascend 时，ascend_value 固定为 high
- migration_method 固定为 auto-inherit 或 cherry-pick

### B6：重复 commit
- 同一 full_sha 只输出一条记录
- 同一 PR 的多个 commit：合并为一条，affected_files 取并集
